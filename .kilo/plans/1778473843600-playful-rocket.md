# .NET 8 → .NET 10 Upgrade Assessment for Pfpad

## Executive Summary

**Recommendation: Upgrade to .NET 10 before November 2026, but NOT immediately — plan a 2-week migration window.**

.NET 8 LTS and .NET 9 STS both die November 10, 2026 (6 months from now). .NET 10 LTS runs to November 2028. The gap window for migration has already opened — doing it now avoids last-minute pressure. However, this is not a trivial TFM bump. There are **compilation-failure-grade risks** (System.Web removal, Roslyn version lift, WebBrowser deprecation) that require real migration work.

---

## Support Lifecycle — The Hard Deadline

| Version | Type | Support Ends |
|---------|------|-------------|
| .NET 8 | LTS | **November 10, 2026** |
| .NET 9 | STS | **November 10, 2026** |
| .NET 10 | LTS | **November 14, 2028** (3 more years) |

In 6 months, both .NET 8 and .NET 9 lose security patches. This is not optional — you **must** be on .NET 10 by November 2026 to remain supported.

## What Breaks — Compilation Failures (Must Fix)

### 1. `System.Web.HttpUtility.HtmlEncode()` — **REMOVED** in .NET 10
- **Location:** `MarkdownPreviewPanel.cs` lines 145, 239, 315
- **Severity:** Compilation error
- **Fix:** Replace with `System.Net.WebUtility.HtmlEncode()` or `System.Text.Encodings.Web.HtmlEncoder.Default.Encode()`
- **Effort:** Trivial (5 minutes, find-and-replace)

### 2. Roslyn 4.8.0 — No `net10.0` TFM
- **Location:** All 5 `Microsoft.CodeAnalysis.*` packages in `.csproj`
- **Severity:** May fail to restore/build, even if it loads via compat
- **Target:** Upgrade to 4.13+ (latest `net8.0`-compatible) or 5.x (native `net10.0` TFM)
- **Effort:** Medium — below

### 3. Roslyn API Breaking Changes
- **`Renamer.RenameSymbolAsync`** is `[Obsolete]` and will be removed in v5.x
  - Found at `RoslynWorkspaceService.cs:173-176` (already suppressed with `#pragma warning disable CS0618`)
  - Must migrate to new overload with `RenameOptions`
- If upgrading to Roslyn 5.x: `Workspace.WorkspaceFailed +=` → `RegisterWorkspaceFailedHandler()`, `DocumentOpened`/`DocumentClosed` event migration
- **Effort:** Medium — 1-2 hours of API migration

### 4. `WebBrowser` Control (IE Trident) — Deprecation Path
- **Location:** `MarkdownPreviewPanel.cs:11, 40-48, 92-105` (entire markdown preview rendering)
- **Severity:** Not yet `[Obsolete]` in .NET 10, but likely to land in a servicing release. Even if functional, IE engine is unsupported by Windows.
- **Fix:** Migrate to `Microsoft.Web.WebView2.WinForms.WebView2` (Chromium-based)
- **Effort:** **HIGH — 1-3 days.** Must rewrite HTML rendering, CSS injection, and interop surface. WebView2 uses `NavigateToString()` and `CoreWebView2` API, very different from `WebBrowser.Document.Write()`.

## What Changes — Behavioral Risks (Must Test)

### 5. Dark Mode — Native vs. Custom
- .NET 10 provides native `Application.SetColorMode(SystemColorMode.System)` with full dark mode support for all built-in controls
- Pfpad already has a sophisticated custom theme system (`ThemeManager`, `Theme` struct, ~20 colors mapped to every control)
- **Risk:** Native dark mode may conflict with custom theme rendering. Native API sets `SystemColors` globally; Pfpad's per-control `BackColor`/`ForeColor` overrides may fight with it.
- **Strategy:** Keep custom theme system. Do NOT enable native dark mode. Continue setting colors explicitly. Native dark mode is irrelevant when you already have a custom theming engine.
- **Effort:** Test everything with the new framework — custom renderers, owner-draw TabControl, GDI+ painting

### 6. RichTextBox + Win32 Messages
- **Locations:** `HighlightRichTextBox.cs`, `Form1.cs` (EM_GETLINE, EM_SETCHARFORMAT, EM_LINESCROLL, WM_SETREDRAW), `MinimapControl.cs`, `FoldingManager.cs`, `IncrementalHighlighter.cs`, `VimEngine.cs`
- The codebase sends raw Win32 messages to the RichTextBox handle for syntax highlighting, line visibility, scroll position, and character formatting
- **Risk:** While Win32 APIs don't change, the RichTextBox managed wrapper may have subtle behavior changes in .NET 10 (e.g., event ordering, DPI handling)
- **Effort:** Full regression test of all syntax highlighting, scrolling, and folding

### 7. NativeWindow Subclass (`TabStripBackgroundWindow`)
- **Location:** `Form1.cs:6686-6734`
- Subclasses `TabControl.Handle` via `NativeWindow.AssignHandle()` to intercept `WM_ERASEBKGND` and `WM_HSCROLL`
- **Risk:** Fragile pattern. If .NET 10 changes message routing, custom WndProc may receive different messages or have different message ordering
- **Effort:** Test tab strip rendering, scrolling, and close button behavior

### 8. `StatusStrip` Default Renderer Change
- .NET 10 changes the default `StatusStrip` renderer from `Professional` to `System`
- **Impact:** Pfpad uses `ThemeAwareMenuRenderer` and `ToolStripProfessionalRenderer` overrides — likely unaffected, but verify status bar renders correctly
- **Effort:** Visual regression test

### 9. New Obsolete Warnings (WFDEV004/005/006)
- `Form.Closing`/`Form.Closed` → `FormClosing`/`FormClosed`
- `Clipboard.GetData()` → `Clipboard.TryGetData<T>()`
- `ContextMenu`, `DataGrid`, `MainMenu`, `Menu`, `StatusBar`, `ToolBar` → modern equivalents
- **Impact:** Warnings only, not errors. Pfpad uses `FormClosing` already (line 438), `ContextMenuStrip` (line 5458). The `Closed`/`Closing` events — checked: Pfpad uses `FormClosing` only (confirming no impact)
- **Effort:** Trivial (verify, possibly suppress warnings)

### 10. C# 14 Stricter Nullable Analysis
- .NET 10 may produce new `CS8618` warnings for fields initialized via methods called from constructors (not direct assignment)
- Pfpad uses `null!` extensively for this pattern (e.g., `minimapMenuItem = null!;`)
- **Effort:** May need to add `= null!;` to additional fields or suppress new warnings

## What Improves — Real Benefits

### Performance
| Benefit | Relevance to Pfpad |
|---------|-------------------|
| **Stack allocation of small arrays** (escape analysis) | Token arrays in `IncrementalHighlighter`, line buffers — reduced GC pressure |
| **Delegate escape analysis** | Lambda closures in UI event handlers — potentially 3x less allocation |
| **Array interface devirtualization** | `foreach` over `IEnumerable<T>` arrays now as fast as direct array iteration |
| **DATAS GC (default)** | Adaptive heap sizing — lower pause times for a desktop app that stays open for hours |
| **JIT PGO + integer value profiling** | `Memmove`/`SequenceEqual` optimized for common sizes |
| **`ReadOnlySpan<T>` support in GDI+** | `Graphics.DrawLines(ReadOnlySpan<Point>)` — fewer allocations in ruler/gutter painting |

### C# Language (C# 12 → C# 14)
| Feature | Usefulness |
|---------|-----------|
| **`field` keyword** | Cleaner property accessors for `_splitEditor`, `_notificationStatusLabel`, etc. |
| **Extension members** | Could extend `RichTextBox`, `Document`, etc. without subclassing |
| **Null-conditional assignment** (`obj?.Property = value`) | Many null-check-then-assign patterns in `Form1.cs` |
| **Implicit Span conversions** | Cleaner interop with `stackalloc` in `FileIconProvider.cs` |
| **`params Span<T>`** | Reduce array allocations in parameter passing |

### Tooling
- **Visual Studio 2026** — required, but unlocks C# 14 and latest Roslyn analysis
- **`dotnet new sln`** defaults to `.slnx` format — no impact, keep `.sln` for compatibility

### Roslyn Upgrade Path Decision

**Option A: Roslyn 4.13.x** (latest `net8.0`-compatible, supports `net10.0` as compile target)
- Pro: Minimal breaking changes from 4.8.0
- Pro: Still works with Visual Studio 17.x (2022)
- Con: Does NOT target `net10.0` natively (runs on `net8.0` compat surface)
- Con: May not support C# 14 syntax analysis fully

**Option B: Roslyn 5.3.x** (native `net10.0` TFM, C# 14)
- Pro: Full C# 14 syntax tree support
- Pro: `net10.0` TFM — native, no compat layer
- Con: Breaking changes: `Renamer.RenameSymbolAsync` removed, workspace events API migration
- Con: Requires Visual Studio 2026 (18.0+)
- Con: MSBuild.Workspaces adds `Microsoft.VisualStudio.SolutionPersistence` dependency for `.slnx` support

**Recommendation: Option B (Roslyn 5.x).** If you're committing to .NET 10, take the native TFM path. The breaking changes are manageable — ~2 hours of API migration for the workspace events and rename symbol API.

## Pfpad Codebase-Specific Risks

### P/Invoke Inventory — All Stable
40+ `DllImport` declarations across 17 files. Every single one calls **standard Win32 APIs** that are not going to change:
- `user32.dll`: `SendMessage`, `GetWindowLong`, `SetWindowLong`, `SetWindowPos`, `GetDC`, `ReleaseDC`, `HideCaret`, `GetSystemMetrics`, window hooks
- `uxtheme.dll`: `SetWindowTheme`
- `gdi32.dll`: `BitBlt`
- `dwmapi.dll`: `DwmSetWindowAttribute`
- `shell32.dll`: `DragAcceptFiles`, `DragQueryFile`, `DragFinish`
- `kernel32.dll`: `GetCurrentThreadId`

**Risk: LOW.** These are Windows OS APIs, not .NET APIs. They are invariant across .NET version upgrades.

### Async Patterns — Bug Found
- `Form1.cs:554`: `EnsureRoslynService().SetAnalyzersEnabledAsync(true).ConfigureAwait(false);`
  - This calls `.ConfigureAwait(false)` on a **fire-and-forget** task (not awaited). The `ConfigureAwait` is meaningless — the returned `ConfiguredTaskAwaitable` is discarded. This is a pre-existing bug, not a .NET 10 issue.
  - Should be: `_ = EnsureRoslynService().SetAnalyzersEnabledAsync(true);` (explicit discard)
  - Or properly awaited

### Font Leaks
- ~80+ `new Font(...)` calls across the codebase, many without `Dispose()`
- .NET 10 may have stricter finalizer behavior for GDI objects
- Not a migration blocker but should be cleaned up eventually

### WinForms Controls — No Structural Changes
- `SplitContainer`, `ToolStrip`, `MenuStrip`, `StatusStrip`, `Panel`, `Label`, `Button`, `TabControl` — all mature, no API removals
- Owner-draw `TabControl` with `DrawMode = OwnerDrawFixed` — behavior unchanged
- `System.Windows.Forms.Timer` — stable

## Honest Assessment

### The Case FOR Upgrading Now
The deadline is November 2026 — 6 months away. You can either do this on your schedule over 1-2 weeks, or under pressure in October-November when something else is on fire. The migration work is real but bounded — ~3 days of actual code changes, ~3 days of testing.

### The Case AGAINST Upgrading Now
If Pfpad is feature-stable and you don't need C# 14, you can delay. .NET 8 continues to receive patches for 6 more months. Delaying gives .NET 10 more time to stabilize (it's ~6 months post-GA now, Patch 7 just released). The WebView2 migration is the biggest unknown — if you delay, the WebBrowser control might get `[Obsolete]` which forces your hand anyway.

### Bottom Line
**Upgrade in the next 1-3 months.** This gives you:
- .NET 10 stabilized (already on patch 7)
- Buffer before the support cliff
- Time to handle any unexpected WebView2 migration issues
- No last-minute panic in October 2026

**Skip .NET 9.** Going from 8 → 10 directly saves you from doing this migration twice. .NET 9 is STS with the same death date as .NET 8.

## Recommended Migration Sequence

1. **Switch TFM** to `net10.0-windows`, install VS 2026
2. **Fix compilation errors:** `System.Web.HttpUtility` → `System.Net.WebUtility`
3. **Upgrade Roslyn** to 5.x, fix obsolete API usage
4. **Verify LibGit2Sharp and TreeSitter** restore and load correctly
5. **Markdown preview:** Migrate `WebBrowser` → `WebView2`
   - `NavigatedToString()` for initial content
   - `CoreWebView2.NavigateToString()` for live updates
   - Keep the same CSS and HTML generation logic
6. **Full regression test:** Open/edit/save files, syntax highlighting, code folding, minimap, goto-def, rename, debugger, git integration, all panels
7. **Cleanup:** Address new nullable warnings, fix font leaks opportunistically
8. **Ship**
